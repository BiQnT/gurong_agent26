# 구룡포 방파제 보행자 안전 경보 에이전트 — 사용 데이터

[API 카탈로그](../../docs/api-catalog/README.md)에서 쓸 API를 고르고, **실제로 호출해본 결과**를 남긴다.
호출해보지 않은 API는 "쓸 예정"으로만 적고 판정란을 비워둔다.

> **2026-08-06 팀 serviceKey로 재검증 완료** (최초 작성 시점엔 키가 없어 401만 확인했었다).
> 처음엔 `INT_S01_004`(대기환경)가 40104(권한 없음)였는데, 같은 날 팀이 "구룡포읍 대기환경"
> 서비스도 추가로 활용 신청해서 승인받았고 이후 재호출로 성공을 확인했다. 4개 API 전부 사용 가능.

## 중요 발견 1: serviceKey는 API(서비스)별로 권한이 갈린다

처음에는 "카탈로그 문서 43개 API가 전부 같은 예시 `serviceKey` 값을 쓰길래 키 하나로 전체를
커버하는 줄 알았는데, 틀렸다. `INT_S06_*`(보행자안전)는 처음부터 됐지만 `INT_S01_004`(대기환경)는
처음엔 **`40104 요청한 API 에 대한 권한 없음`** 을 받았다 — **서비스별로 활용 신청이 따로
필요**하다는 뜻이다. E-UM 포털에서 "구룡포읍 대기환경" 서비스를 추가로 신청해서 해결했다.
**팀에서 새 API를 쓰려면 그때그때 해당 서비스를 개별적으로 신청해야 한다는 걸 기억할 것.**

## 중요 발견 2: 카탈로그 문서의 필드명 오타 (`temper` → `temp`)

`docs/api-catalog/01-대기환경.md`를 보고 온도 필드를 `temper`로 짐작해서 코드에 그렇게 썼는데,
실제 승인 후 호출해보니 응답 필드는 `temp`였다 (문서에도 실제로는 `temp`라고 정확히 적혀 있었다 —
내가 처음 옮길 때 잘못 읽은 것). `prototype/server.py`, `prototype/monitor.py`에서
`atmo.get("temper")` → `atmo.get("temp")`로 수정 완료. **"카탈로그 문서에 있다"와 "내가 정확히
옮겨적었다"는 다르다 — 실제 응답으로 반드시 재확인해야 한다는 교훈.**

## 호출 기록

### INT_S06_006 — 시간대별 이상행동 발생수 통계

**요청**

```bash
curl -s "https://genix.pohang-eum.kr/dpg/aicctv/avghour/datas?serviceKey=$EUM_SERVICE_KEY"
```

**응답 (실제, 2026-08-06 14:0*경, 팀 serviceKey)**

```json
{
  "id": "1",
  "status": "success",
  "data": {
    "south": [
      {"hour": "2026-08-06 04:00:00", "warningFallDetectionCount": 0, "warningInsideDetectionCount": 0, "warningApproachCount": 0, "normalFallDetectionCount": 0},
      { "...": "05시~13시, 10개 시간대 전부 0건" }
    ],
    "north": [
      { "...": "south와 동일하게 10개 시간대 전부 0건" }
    ]
  }
}
```

**확인한 것**

- 데이터가 실제로 들어오는가: **예**, 정상 응답. 다만 조회 시점(평일 오후)엔 남/북 방파제 전부
  이상행동 4종이 전부 0건이었다 — 실증 데이터가 비어있진 않지만 "위험" 판정을 보여줄 실제
  사례는 아직 못 봤다 (시연 때는 인위적으로 이상행동이 있는 시간대를 찾거나, 담당 부서에 성수기
  샘플 데이터를 요청해야 할 수도 있음)
- 갱신 주기 / 최신 데이터 시각: `hour` 기준 시간 단위, 최근 10개 시간대(당일 04시~13시)를 배열로
  줌. 시간대 정렬은 오름차순으로 보인다
- 좌표계, 시간대(KST/UTC), 단위: `hour`는 `YYYY-MM-DD HH:00:00`, KST로 확인
- 구룡포 지역을 커버하는가: 예 (서비스 자체가 구룡포 방파제 전용)
- 호출 제한이 있는가: 미확인 (연속 호출 몇 차례는 문제 없었음)

**막힌 것 / 이상한 것**

- 파라미터 없이 호출하면 항상 "오늘 최근 10개 시간대"만 주는 것으로 보인다 — 특정 날짜를
  지정하는 파라미터는 문서에도 없고 실제로도 안 먹힌다. 과거 데이터로 데모하려면 이 API로는
  안 되고 다른 방법이 필요함 (범위 밖으로 보류)
- 응답 껍데기는 카탈로그 문서 그대로 `{id, status, data}` — 인증/권한 실패일 때만
  `{rspns_rslt, rspns_bdy}` 형태였다. `prototype/eum_client.py`가 이미 두 형태를 다 처리하므로
  코드 수정은 불필요

### INT_S06_001 — 보행자 예측 관련 장비 정보 목록

**요청**

```bash
curl -s "https://genix.pohang-eum.kr/dpg/pedestrian/device/list?serviceKey=$EUM_SERVICE_KEY"
```

**응답 (실제, 2026-08-06, 팀 serviceKey — 일부)**

```json
{
  "id": "1",
  "status": "success",
  "data": {
    "speakers": [
      {"id": 1, "name": "구룡포 북방파제 SR-01-001", "latitude": "35.985667", "longitude": "129.557917", "address": "포항시 남구 구룡포읍 구룡포리 954-3"},
      {"id": 2, "name": "구룡포 북방파제 SG-01-001", "latitude": "35.987417", "longitude": "129.558556", "address": "포항시 남구 구룡포읍 구룡포리 954-3"},
      {"id": 7, "name": "구룡포 남방파제 SR-02-001", "latitude": "35.984917", "longitude": "129.559167", "address": "포항시 남구 구룡포읍 병포리 1-5"},
      { "...": "총 8개 (북방파제 5개: SG-01/02/03, SR-01 / 남방파제 3개: SG-10/11/12, SR-02)" }
    ],
    "ai_cctvs": [{ "...": "총 15개, 북방파제 7개 / 남방파제 8개" }],
    "uv_devices": [{"id": 6, "name": "자외선 측정기", "latitude": "35.98524", "longitude": "129.551826", "address": "경북 포항시 병포리 157-294"}]
  }
}
```

**확인한 것**

- 데이터가 실제로 들어오는가: 예, 정상 응답
- 갱신 주기 / 최신 데이터 시각: 정적 장비 목록 (설치 정보라 실시간성 없음)
- 좌표계, 시간대(KST/UTC), 단위: 위경도(WGS84로 추정). 스피커 1개(`구룡포 남방파제 SG-10-001`)는
  위경도·주소가 빈 문자열이었다 — 설치 예정이거나 좌표 미등록 장비로 추정
- 구룡포 지역을 커버하는가: 예
- 호출 제한이 있는가: 미확인
- 자외선 측정기는 **1대뿐**이다 (병포리 소재). 남/북 방파제 각각에 자외선계가 있는 게 아니라
  방파제 지역 전체에 값 1개만 쓴다는 뜻 — README 3번의 "자외선 데이터를 함께 본다"는 지역
  전체 조건이지 구역별 조건이 아니다 (이미 `server.py` 설계와 일치함)

**막힌 것 / 이상한 것**

- 예상대로 구역(남/북)을 나타내는 명시적 필드는 없다. 대신 장비명 자체에 "북방파제"/"남방파제"가
  포함돼 있어서 문자열 매칭이 실제로 통한다(`prototype/server.py`의 `_find_speaker_for_zone`에서
  검증 완료) — 실제 응답으로 이 가정이 맞다는 게 확인됐다
- 스피커가 `SR-`, `SG-` 두 접두사로 나뉘는데(용도 차이로 추정 — 방송용/경광등 등) 카탈로그 문서엔
  설명이 없다. 확인 필요하면 주최 측에 문의

### INT_S06_005 — 자외선 측정 장비 실시간 수집 정보

**요청**

```bash
curl -s "https://genix.pohang-eum.kr/dpg/sensor/latest/uvIndex?serviceKey=$EUM_SERVICE_KEY"
```

**응답 (실제, 2026-08-06 13:39:37, 팀 serviceKey)**

```json
{"id": "1", "status": "success", "data": {"dateTime": "2026-08-06 13:39:37", "uvIndex": 4.9}}
```

**확인한 것**

- 데이터가 실제로 들어오는가: 예, 호출 시점 기준 약 몇 분 전 데이터
- 갱신 주기 / 최신 데이터 시각: 위 예시 기준 수 분 단위로 갱신되는 것으로 보임
- 좌표계, 시간대(KST/UTC), 단위: KST, UV Index (무차원, 4.9는 "보통~높음" 사이)
- 구룡포 지역을 커버하는가: 예 (자외선계는 1대뿐, 위 INT_S06_001 확인 참고)
- 호출 제한이 있는가: 미확인

**막힌 것 / 이상한 것**

- (해결됨) 장비가 1대뿐이라 장비 ID 지정 파라미터가 애초에 필요 없었다

## 응답 껍데기 정리 (확정)

- **정상 응답**: `{ "id", "status": "success", "data": {...} }` — 카탈로그 문서와 정확히 일치
- **인증/권한 실패**: `{ "rspns_rslt": { "rslt_cd", "rslt_msg" }, "rspns_bdy": null }`
  - `40102` = 유효하지 않은 서비스 키
  - `40104` = 이 키로는 해당 API(서비스)에 대한 권한 없음
- `prototype/eum_client.py`가 두 형태를 모두 처리하도록 이미 작성돼 있어 코드 수정 불필요

## 데이터 공백

이 아이디어가 성립하려면 필요한데 **어디에도 없는** 데이터. 있으면 솔직히 적고 대안을 쓴다.

| 필요한 데이터 | 없는 이유 | 대안 |
| --- | --- | --- |
| 스피커 원격 방송 제어 API | 카탈로그 43개 API 중 스피커는 위치 조회만 있고 제어(송출) API가 없음 | MVP는 "어느 스피커로 방송해야 하는지 추천"까지만 하고, 실제 송출은 담당자가 수동으로 수행 |
| 대기환경(풍속) 데이터 접근 권한 | 팀 serviceKey가 아직 "구룡포읍 대기환경" 서비스에 대해 승인되지 않음 (40104) | E-UM 포털에서 대기환경 서비스도 추가로 활용 신청 — 승인 전까지 `assess_breakwater_risk`는 풍속 없이 이상행동+자외선만으로 판정 (실제로 이렇게 degrade 하도록 이미 구현됨) |
| 이상행동이 실제로 잡힌 시간대 샘플 | 확인 시점(2026-08-06 평일 오후)엔 최근 10시간 전부 0건이었음 | 성수기/주말 등 다른 시간대에 재호출해서 "위험" 판정 실사례 확보, 또는 주최 측에 샘플 데이터 시점 문의 |
