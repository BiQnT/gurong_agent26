# 구룡포 방파제 보행자 안전 경보 에이전트 — 사용 데이터

[API 카탈로그](../../docs/api-catalog/README.md)에서 쓸 API를 고르고, **실제로 호출해본 결과**를 남긴다.
호출해보지 않은 API는 "쓸 예정"으로만 적고 판정란을 비워둔다.

> **serviceKey 미발급 상태로 작성**. E-UM 로그인 후 API 자료실에서 팀 serviceKey를 발급받으면
> 아래 curl을 그대로 재실행해서 실제 응답으로 이 문서를 업데이트해야 한다.
> 지금까지 확인한 것은 "엔드포인트가 살아있고, 인증만 통과하면 호출 가능한 상태"까지다.

## 요약

| API ID | 엔드포인트 | 호출 테스트 | 판정 |
| --- | --- | --- | --- |
| `INT_S06_006` | `/dpg/aicctv/avghour/datas` | 실패 (401, 인증키 없음 — 엔드포인트 생존 확인) | 사용 |
| `INT_S06_001` | `/dpg/pedestrian/device/list` | 실패 (401, 인증키 없음 — 엔드포인트 생존 확인) | 사용 |

| `INT_S01_004` | `/dpg/atmosphere/device/realtime` | 미시도 (001 아이디어에서 이미 성공 확인됨, 재확인 필요) | 보류 |

## 호출 기록

### INT_S06_006 — 시간대별 이상행동 발생수 통계

**요청**

```bash
curl -s "https://genix.pohang-eum.kr/dpg/aicctv/avghour/datas?serviceKey=$EUM_SERVICE_KEY"
```

**응답 (실제, 2026-08-06 · 테스트용 키로 호출)**

```json
{"rspns_rslt": {"rslt_cd": "40102", "rslt_msg": "유효하지 않은 이용자 서비스 키"}, "rspns_bdy": null}
```

**확인한 것**

- 데이터가 실제로 들어오는가: 확인 못함 — 유효한 serviceKey 필요
- 갱신 주기 / 최신 데이터 시각: 카탈로그 문서상 `hour` 필드로 시간대별 제공 (실측 필요)
- 좌표계, 시간대(KST/UTC), 단위: 카탈로그 예시가 `2026-07-08 08:00:00` 형식 — KST로 추정, 확인 필요
- 구룡포 지역을 커버하는가: 서비스 자체가 구룡포 방파제 AI CCTV 전용이므로 커버 확실
- 호출 제한이 있는가: 미확인

**막힌 것 / 이상한 것**

- 파라미터 없이 호출하는 형태라 남/북 방파제(`south`/`north`)를 개별 필터링할 방법이 카탈로그 문서에 명시돼 있지 않음. 응답 전체를 받아 클라이언트에서 나눠야 할 수도 있음 — 실제 응답 받으면 확인

### INT_S06_001 — 보행자 예측 관련 장비 정보 목록

**요청**

```bash
curl -s "https://genix.pohang-eum.kr/dpg/pedestrian/device/list?serviceKey=$EUM_SERVICE_KEY"
```

**응답 (실제, 2026-08-06 · 테스트용 키로 호출)**

```json
{"rspns_rslt": {"rslt_cd": "40102", "rslt_msg": "유효하지 않은 이용자 서비스 키"}, "rspns_bdy": null}
```

**확인한 것**

- 데이터가 실제로 들어오는가: 확인 못함 — 유효한 serviceKey 필요
- 갱신 주기 / 최신 데이터 시각: 정적 장비 목록이라 실시간성 없음 (설치 정보)
- 좌표계, 시간대(KST/UTC), 단위: 위경도(WGS84로 추정)
- 구룡포 지역을 커버하는가: 예 (uv_devices/speakers/ai_cctvs 모두 구룡포 방파제 설치분)
- 호출 제한이 있는가: 미확인

**막힌 것 / 이상한 것**

- 스피커(`speakers`)와 CCTV(`ai_cctvs`)가 이름·주소는 있지만 "어느 구역(남/북)"인지 나타내는 필드가 명시적으로 없음. `name`에 "북방파제"가 포함되는 패턴(예: `구룡포 북방파제 SR-01-001`)으로 문자열 매칭해야 할 가능성 — 실제 응답으로 검증 필요

### INT_S06_005 — 자외선 측정 장비 실시간 수집 정보

**요청**

```bash
curl -s "https://genix.pohang-eum.kr/dpg/sensor/latest/uvIndex?serviceKey=$EUM_SERVICE_KEY"
```

**응답 (실제, 2026-08-06 · 테스트용 키로 호출)**

```json
{"rspns_rslt": {"rslt_cd": "40102", "rslt_msg": "유효하지 않은 이용자 서비스 키"}, "rspns_bdy": null}
```

**확인한 것**

- 데이터가 실제로 들어오는가: 확인 못함 — 유효한 serviceKey 필요
- 갱신 주기 / 최신 데이터 시각: 카탈로그 예시 `2026-07-08 17:21:17`
- 좌표계, 시간대(KST/UTC), 단위: 시간대 KST로 추정, 단위는 UV Index (무차원)
- 구룡포 지역을 커버하는가: 예
- 호출 제한이 있는가: 미확인

**막힌 것 / 이상한 것**

- 장비 ID로 특정 위치를 지정하는 파라미터가 카탈로그 문서에 없음 (전체 최신값만 주는 것으로 보임) — 여러 자외선 측정기 중 방파제 것만 골라야 한다면 `INT_S06_001`의 `uv_devices` 목록과 대조 필요

## 응답 껍데기 관찰 (공통)

카탈로그 문서(`docs/api-catalog/README.md`)는 정상 응답 껍데기를 `{ id, status, data }`로 설명하지만,
실제 인증 실패 응답은 `{ rspns_rslt: { rslt_cd, rslt_msg }, rspns_bdy }` 형태였다. 정상 응답도 이
`rspns_bdy` 껍데기를 쓸 가능성이 있으므로, MCP 서버는 두 형태(`data` 키 / `rspns_bdy` 키)를 모두
방어적으로 파싱하도록 만들었다 (`prototype/eum_client.py` 참고). 유효한 키로 재호출해서 확인 필요.

## 데이터 공백

이 아이디어가 성립하려면 필요한데 **어디에도 없는** 데이터. 있으면 솔직히 적고 대안을 쓴다.

| 필요한 데이터 | 없는 이유 | 대안 |
| --- | --- | --- |
| 스피커 원격 방송 제어 API | 카탈로그 43개 API 중 스피커는 위치 조회만 있고 제어(송출) API가 없음 | MVP는 "어느 스피커로 방송해야 하는지 추천"까지만 하고, 실제 송출은 담당자가 수동으로 수행 |
| 남/북 방파제 구역 코드 필드 | `INT_S06_006`, `INT_S06_001` 모두 구역을 명시적 필드로 주는지 문서상 불확실 | 실제 응답 확인 후, 없으면 장비명 문자열 패턴("북방파제"/"남방파제")으로 구역 매핑 |
