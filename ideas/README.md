# 아이디어

아이디어 하나 = 폴더 하나 = 브랜치 하나. 문서, 코드, 데이터 조사 결과를 전부 그 폴더 안에 모은다.

8월 1주차(~8.9)에 여기 모인 아이디어를 심사 기준 4항목으로 비교해서 **하나를 확정**한다.
확정된 아이디어만 `main`에 머지하고 나머지 브랜치는 남겨둔다 (기획서의 "검토한 대안"으로 쓸 수 있다).

## 만드는 법

```bash
scripts/new-idea.sh <slug> "아이디어 한 줄 제목"
# 예: scripts/new-idea.sh breakwater-guard "방파제 보행자 위험 경보 에이전트"
```

스크립트가 하는 일:

1. `main`에서 `idea/NNN-<slug>` 브랜치를 판다
2. `ideas/NNN-<slug>/`에 템플릿을 복사한다
3. 제목·번호·날짜를 채워 넣는다

수동으로 해도 된다. `_template/`을 복사해서 `ideas/NNN-<slug>/`로 두면 끝이다.

## 폴더 구조

```
ideas/NNN-<slug>/
  README.md      아이디어 원페이저 — 문제, 사용자, 에이전트 동작, 차별성, 범위, 리스크, 자체 점수
  data.md        쓸 데이터 — 카탈로그 API ID와 연결, 호출 테스트 결과
  prototype/     돌아가는 코드 조각 (없어도 됨. 있으면 실현 가능성 점수에 크게 유리)
```

## 규칙

- **브랜치명**: `idea/NNN-<slug>` — slug는 영문 소문자와 하이픈만
- **한 브랜치는 자기 아이디어 폴더만 건드린다.** 다른 아이디어 폴더나 `docs/`를 같이 고치면 비교할 때 diff가 지저분해진다
- **PR은 아이디어가 어느 정도 정리된 뒤에 연다.** 초안 단계에서는 그냥 브랜치에 푸시만 해도 된다
- **쓸 데이터는 반드시 카탈로그의 API ID로 특정한다** (`INT_S06_006` 형식).
  "대기질 데이터를 활용"처럼 뭉뚱그리면 실현 가능성 검증이 안 된다
- **호출해보지 않은 API를 "쓸 수 있다"고 적지 않는다.** `data.md`에 실제 요청·응답을 남긴다

## 왜 이렇게 하나

서면평가 배점 100점 중 55점이 '구체성·논리성(30)'과 '실현 가능성(25)'이다.
아이디어를 문서로만 적어두면 이 55점을 증명할 방법이 없다.
폴더에 **실제 호출한 API 응답**과 **돌아가는 코드 조각**이 같이 있으면
기획서의 "기술적 구현 방법"에 그대로 옮겨 쓸 수 있다.
