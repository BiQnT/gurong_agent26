# 0001. 프로젝트 컨텍스트를 노션과 레포로 나눠 관리

- **날짜**: 2026-07-26
- **상태**: 확정
- **관련**: [노션 팀 페이지](https://app.notion.com/p/183d9a77d21882288fe501ad8fc2397d), `CLAUDE.md`

## 맥락

노션과 깃허브 레포를 동시에 쓰기 시작하면서 같은 내용이 양쪽에 생길 위험이 있다.
실제로 두 가지가 이미 발생했다.

- `docs/회의록/`이 빈 채로 만들어져 있는데 노션에도 회의록 페이지가 있다
- E-UM API 카탈로그가 레포(`docs/api-catalog/`)와 노션 양쪽에 있다

앞으로 결정사항·진행사항·파이프라인 설계가 쌓이면 이 문제는 커진다.
문서가 낡는 이유는 대부분 "같은 사실이 두 곳에 있는데 한 곳만 고쳐서"다.

## 결정

**경계 기준은 "이걸 PR에서 리뷰받아야 하나?"** 하나다.

| | 노션 | 레포 |
| --- | --- | --- |
| 성격 | 상태가 자주 바뀜, 사람이 브라우저에서 편집 | 이력·리뷰가 필요함, 코드와 함께 변함 |
| 담는 것 | 진행 상황 트래커, 회의록, 제출 서류 체크리스트, 팀원 정보 | 결정 기록(ADR), 설계 문서, API 스펙, 아이디어, 코드 |
| 안 담는 것 | 설계·스펙 원본 | 진행 상태, 담당자, 마감일 |

운영 규칙 다섯 가지:

1. **한 사실 = 한 장소.** 두 번째 위치에는 링크만 둔다.
2. **부득이한 사본에는 날짜와 정본 링크를 단다.** `YYYY-MM-DD 스냅샷 · 정본: <링크>`
3. **생성할 수 있으면 생성한다.** 손으로 쓴 문서만 낡는다.
4. **기록은 고치지 않는다.** ADR·회의록·API 호출 로그는 append-only.
5. **서술형 문서는 최소로.** "현재 구조는 이렇다"가 낡음의 온상이다.

## 이유

두 매체의 성질이 다르다. 노션은 상태 추적과 사람 협업에 강하지만 diff·리뷰·이력이
없다. 레포는 그 반대다. 각자 잘하는 것만 맡기면 중복이 생길 자리가 줄어든다.

규칙 3이 가장 강력하다. `docs/api-catalog/`는 `fetch_eum_catalog.py`가 만들고
사람이 손대지 않는다. E-UM이 API를 추가하면 스크립트를 다시 돌려 diff를 보면 되고,
낡을 수가 없다. 앞으로도 생성 가능한 것은 생성한다.

규칙 4는 이 프로젝트에서 특히 값싸다. 대회 기간이 두 달이라 문서를 관리할 여력이
없다. 낡지 않는 형식으로 적어두면 관리 자체가 필요 없다.

## 검토한 대안

| 대안 | 왜 안 골랐나 |
| --- | --- |
| 전부 노션 | diff·PR 리뷰가 없다. 코드와 설계가 떨어져 있으면 코드를 고칠 때 설계 문서가 보이지 않아 반드시 낡는다 |
| 전부 레포 | 팀원이 진행 상황을 보려고 git을 켜야 한다. 캘린더·보드 같은 상태 추적 UI가 없다 |
| 레포에 위키 폴더를 따로 만들기 | `docs/`와 무엇이 다른지 규칙을 못 세운다. 폴더가 하나 늘면 "어디에 쓰지?" 고민만 늘어난다 |
| 양쪽 동기화 자동화 | 두 달짜리 대회에서 동기화 스크립트를 만들고 유지하는 비용이 얻는 것보다 크다 |

## 결과

**쉬워지는 것**

- "이걸 어디에 쓰지?"에 한 문장으로 답할 수 있다
- 에이전트가 `CLAUDE.md`의 지도를 보고 정본만 읽는다
- 아이디어가 폐기돼도 그 브랜치의 ADR이 남아 기획서의 "검토한 대안"이 된다

**감수하는 것**

- 노션 API 카탈로그는 수동 사본이다. E-UM이 API를 추가하면 레포는 스크립트로
  갱신되지만 노션은 손으로 고쳐야 한다. 사본에 수집일을 박아 낡음이 드러나게 했다
- 회의 결정을 노션 회의록과 ADR 두 번 적어야 한다. 논의 과정은 노션, 결정은 ADR

**되돌리려면**

규칙일 뿐이라 코드 변경이 없다. 새 ADR로 대체하면 된다.
