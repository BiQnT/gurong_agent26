# 0012. 초대 토큰을 서버 비밀값의 HMAC 으로 만들어 대기 중인 초대 링크를 다시 복사한다

- **날짜**: 2026-10-09
- **상태**: 확정
- **정한 사람**: 안동현
- **관련**: 1차 QA (초대 관리), [0006](0006-shared-db-validation-order.md), [workspace-api.md 계정·초대 수명](../design/workspace-api.md#계정초대-수명), [server/workspace.ts](../../server/workspace.ts)

## 맥락

1차 QA 에서 운영자가 초대 링크를 만든 창에서만 한 번 복사할 수 있고, 화면을 떠나면 링크를 다시 볼 수 없어 초대를 취소하고 새로 만들어야 했다. 지금 서버는 32바이트 난수 토큰을 만들고 저장소에는 SHA-256 해시(`tokenHash`)만 둔다. 원문이 없으니 다시 보여 줄 방법이 없다.

원문을 그대로 저장하면 쉽지만 DB 사본·백업이 새면 대기 중인 초대를 모두 쓸 수 있다. 저장 문서에 새 칸을 더하면 `validDatabase` 를 넓혀야 하고, dev·prod 가 DB 를 같이 쓰므로 [0006](0006-shared-db-validation-order.md) 의 배포 순서가 필요하다.

## 결정

- 서버 비밀값 `INVITE_LINK_SECRET` 이 있으면 새 초대 토큰을 `base64url(HMAC-SHA256(비밀값, "invite:" + 초대 ID))` 로 만든다. 길이는 지금 토큰과 같은 43자다.
- 저장하는 것은 지금처럼 토큰의 SHA-256 해시뿐이다. 저장 문서 형식과 `validDatabase`·`validateOperationsData` 는 바뀌지 않는다.
- 운영자 전용 `GET /api/sites/:id/invitations/:invitationId/link` 가 대기 중이고 만료·취소·수락되지 않은 초대의 토큰을 다시 계산한다. 다시 계산한 토큰의 해시가 저장된 `tokenHash` 와 같을 때만 돌려준다. 다르면(비밀값 없이 만든 난수 초대, 비밀값을 바꾸기 전 초대) `409 INVITE_LINK_UNAVAILABLE` 이다.
- 팀 목록의 `Invitation.linkAvailable` 로 다시 복사할 수 있는 초대만 화면에 "링크 다시 복사" 버튼을 보인다. 비밀값이 없으면 모두 false 라서 지금과 같이 동작한다.
- dev·prod 는 같은 DB 를 쓰므로 같은 비밀값을 둔다. 값이 다르면 한쪽에서 만든 초대를 다른 쪽에서 다시 복사할 수 없다(링크는 그대로 쓸 수 있다).

## 검토한 대안

| 대안 | 왜 안 골랐나 |
| --- | --- |
| 토큰 원문을 저장 | DB·백업이 새면 대기 중인 초대를 바로 쓸 수 있다. 세션·초대를 해시로만 두던 원칙과 어긋난다 |
| 토큰을 비밀값으로 암호화해 새 칸에 저장 | 저장 형식과 `validDatabase` 를 바꿔야 해서 0006 의 배포 순서가 필요하다. HMAC 은 같은 일을 저장 없이 한다 |
| 다시 복사 대신 "같은 언어로 새 초대 만들기" 버튼 | 이미 보낸 링크가 대기 중으로 남아 목록이 길어지고, 받은 사람이 어느 링크를 써야 하는지 헷갈린다 |

## 결과

- 쉬워지는 것: 운영자가 대기 중인 초대 링크를 언제든 다시 복사해 보낼 수 있다. 저장 형식이 같아 0006 의 순서 없이 배포한다.
- 감수하는 것: 비밀값이 새면 그 값으로 만든 대기 중 초대의 링크를 초대 ID 만으로 만들 수 있다. 초대 ID 는 운영자 화면에만 보이지만, 비밀값은 키와 같은 수준으로 다룬다. 의심되면 값을 바꾼다. 그 전 초대는 다시 복사만 안 되고 링크는 7일 동안 유효하므로, 필요하면 대기 중인 초대를 취소한다.
- 되돌리려면: `INVITE_LINK_SECRET` 을 지우고 재시작한다. 새 초대는 다시 난수로 만들어지고 버튼이 사라진다. 저장 형식이 같아 데이터는 손대지 않는다.
